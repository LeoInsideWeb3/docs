1 · 总览与决策

永续全面转向 A-Book

平台退出永续对手方角色：订单簿、K线、24h 统计直接采用币安数据；用户订单全部经做市商（MM）在币安真实执行；平台保留账户、保证金、清算与手续费体系，赚取显式手续费，不再承担内部撮合与对手方市场风险。

决策点结论含义
MM 角色Principal（对手方）MM 用自有币安账户对冲；与我方按 house 账户净额定期结算
成交价格币安真实成交价 + 显式手续费费率走 fee_engine 现有体系；点差不进价格
切换范围全量切换所有永续市场一次切 A-Book；无存量持仓（从新开始）
行情与映射以币安为准执行 / 行情 / K线全以币安为准；仅维护我方 ↔ 币安 symbol 映射
接口现状NeoDAX ↔ MM 未建MM 已对接币安；我方与 MM 之间的契约 = 本文档第 3 页（过会材料）

2 · 架构

现状 → 目标：替换"撮合引擎"，保留一切契约

改造的核心洞察：Finex 对外只暴露两个 Kafka 契约——入口 commands.{MKT}.OrderCommands、出口 events.{MKT}.EventOrderUpdated + events.{MKT}.EventTradeExecuted。把消费入口、生产出口的角色换成 mm-connector，下游全部服务零改动。

现状（B-Book 内部撮合）

trading-api边缘网关

① gRPC LockPerpAsset 锁保证金（失败即拒单）→ ② 发布 CommandOrderCreate 到 commands.{MKT}.OrderCommands；发布失败回滚解锁（order_operation_core.go:328-351）。

↓ Kafka
Finex perp内存撮合 · 3 shard

价格-时间优先撮合用户之间的订单；输出订单簿增量（orderbook.{MKT}）与成交/订单事件。用户互为对手方。

↓ EventTradeExecuted（maker + taker 均为内部账户）
PM Perp双参与者结算

Settlement.HandleTrade 对 maker/taker 双方各自更新仓位、已实现盈亏、费用、保证金；清算时保险金/清算池系统账户（owner=0x0）承接对手腿（CLEARING_MIRROR），takeover/ADL 处置坏账。

↓ 成交事件
ledger / analytics数据侧

ledger 聚合内部成交 → Timescale K线/ticker；mark oracle 的数据源之一是 InternalPerpTradeCollector（内部成交自价）。

目标（A-Book 经 MM 执行）

trading-api不变

下单/锁仓/回滚路径完全不变。仅订单簿、K线、ticker、公共成交流的数据源换成 quote 的币安镜像（同 topic 同格式）。

↓ Kafka commands.{MKT}.OrderCommands（同一 topic，消费者换人）
mm-connector新增 · 替代 Finex 的位置

消费订单命令 → MM REST 提交（幂等 + expires_at）→ WS 回报驱动状态机 → 把 ack/成交/撤单/拒绝翻译成 EventOrderUpdated、EventTradeExecuted（house 合成单做对手腿）→ 发布到 events.{MKT}.*。内置：UNKNOWN 悬挂仲裁（判死三条件，见 3.5）、心跳熔断、三方对账 worker。

↓ REST / WS（第 3 页契约） · MM → 币安执行
PM Perp结算语义不变 + house 账户

仍消费 EventTradeExecuted 做双参与者结算——只是对手腿从"另一个用户/系统账户"固定为 MM house 系统账户（UUID 尾号 09，owner=0x0）。清算平仓指令发给 connector；takeover/ADL 退役，保险金只兜穿仓差额。

↓ 币安公共流（quote 镜像，第 6 页）
quote + ledger数据面切换

quote 订阅币安 depth/kline/ticker/aggTrade，以现有格式发布；ledger 的 perp 市场 K线数据源从"内部成交聚合"切到"币安 K线直写"（per-market 开关）；InternalPerpTradeCollector 对 A-book 市场停用。

为什么否决 Kafka-native 方案

另一条路是让 MM 直接消费/生产我们的 Kafka topic（省掉 connector）。否决理由：

  1. 安全边界 — 需要把 Kafka 集群网络与凭证暴露给外部团队，consumer group、rebalance、lag 管理责任全部外移，事故面不可控。
  2. 耦合演进 — 内部事件 schema（如 EventTradeExecuted 加字段）会直接破坏外部消费者；REST/WS 契约让我们可以独立演进内部格式。
  3. MM 实现成本 — MM 团队熟悉的是币安式 REST/WS。接口语义镜像币安（下单/撤单/执行流），他们的实现几乎是零学习成本。
  4. 治理 — connector 是我们的一等公民服务：限速、熔断、对账、审计日志都在我们侧，可观测可运维。

3 · MM 接口契约 v1

NeoDAX ↔ MM 通信契约（过会材料）

这是整个项目第一个要落地的东西。设计原则：语义镜像币安 USDⓈ-M API（下单/撤单/执行回报流），MM 按他熟悉的模型实现；我方 mm-connector 作为唯一调用方，MM 不接触我方 Kafka。

契约要点速览
REST 提交/查询 + WebSocket 回报 · HMAC 认证
client_order_id 幂等（= 我方订单 UUID）· expires_at 防悬挂
ack ≤ 500ms · 市单回报 ≤ 3s · 数值一律字符串小数（禁止 float）

3.0 数据所有权：谁存什么，谁说了算

先回答一个架构级问题：用户的一切状态都存在我方，MM 只是执行反馈的来源。用户侧任何读写都不透传到 MM——这是本契约刻意保持最小（提交 + 回报 + 对账）的原因。

数据权威归属说明
用户订单 / 仓位 / 余额 / 成交历史我方 PM Perpperps_orders / perps_positions / perps_balances / perps_transactions + Raft FSM——现网结构不变
用户读接口（REST / WS 私有流）我方本地trading-api → PM Perp gRPC，与现网一致；永不查 MM——MM 挂了只影响下单，不影响查询
MM 侧订单 / 仓位状态MM（执行反馈）只是我方状态机的输入，不是账本；GET 仅用于仲裁与对账（见下）

状态机的三条更新路径

路径角色触发条件
WS 回报（TRADE_FILL / ORDER_UPDATE）主路径事件驱动、延迟最低；connector 收到即合成 Finex 格式事件进我方 Kafka → PM Perp / trading-api / ledger 照常消费（与现网消费 Finex 事件完全相同）
GET /orders/{id} 仲裁兜底仅三类触发：ack 超时（500ms）· WS 断线重连 · 周期对账——不是常规同步手段
我方内部 Kafka下游分发connector 是唯一翻译点；MM 不接触我方 Kafka（第 2 页否决理由）

3.4 WebSocket 执行流（WS /api/v1/stream）

connector 全程保持一条 WS（断线重连后先对在途与 UNKNOWN 单跑一轮 GET 仲裁再恢复）。消息信封：{type, client_order_id, mm_order_id, transact_time, ...}。

type触发专有字段
TRADE_FILL币安逐笔成交fill_id, qty, price, role(maker|taker), transact_time
ORDER_UPDATE状态迁移state(OPEN→PARTIALLY_FILLED→FILLED), cumulative_qty
ORDER_ACK异步 ack（与 REST 结果二选一，先到为准）mm_order_id, binance_order_id
ORDER_REJECT异步拒绝error_code, message
CANCEL_ACCEPTED撤单成功remaining_qty
CANCEL_REJECTED撤单失败reason(FILLED|UNKNOWN_ORDER|...)
HEARTBEAT每 5sserver_time, binance_connected(bool)
 
// TRADE_FILL —— 核心消息：用户成交价 = 此处的 price（币安真实成交价）
{
  "type":            "TRADE_FILL",
  "client_order_id": "3f9c2a48-...",
  "fill_id":         "MM-F-001283",   // MM 侧唯一，幂等去重用
  "qty":             "5.00",
  "price":           "199.40",         // 币安成交价（可能多笔不同价）
  "role":            "taker",          // maker|taker → 决定我方收哪种费率
  "transact_time":   "2026-10-01T08:00:00.871Z"
}

为什么 role 重要

我方锁仓时按订单类型预收费率（post_only 按 maker 锁），结算时按 MM 回报的币安成交角色计费：限价单挂上后被动成交 → role=maker → 收 maker 费率；吃单 → taker 费率。与现网 Finex 的 maker/taker 语义完全对齐，fee_engine 无需改动。

3.5 幂等 · 悬挂 · 仲裁

必须关闭的竞态窗口（评审意见 2026-09-25）

500ms 时 GET 查无记录 ≠ 该单不会执行：POST 可能仍在网络或 MM 队列里，800ms 才到达且未过期（默认有效期 3s）——若此时解锁保证金、用户转走资金，随后到达的成交将没有保证金背书。expires_at 只约束"MM 收到时"，不约束"我方何时可判死"。

  1. 提交即带 expires_at（我方时钟 + 2 × RTT + 处理余量，默认 3s）MM 收到时已过期的请求必须返回 EXPIRED 拒单且不得执行——有效期是死亡判决的时间前提，不是充分条件（见第 2 条）。
  2. ack 超时（500ms）→ 订单进入 UNKNOWN，保证金保持锁定超时只说明"没等到 ack"，不说明"MM 没收到"。判死必须同时满足三个条件：① 已过 expires_at + 时钟偏移余量（默认 +1s）；② 此时 GET 仍无记录；③ MM 对该 client_order_id 提供不可再执行的终态保证（tombstone，第 3 条）。未到期前的"查无"一律视为 UNKNOWN 持锁，对用户呈现为 pending。
  3. MM 侧 tombstone 保证（契约新增）MM 首次对某 client_order_id 应答 GET "无记录"时必须持久化该应答；此后迟到的同 ID POST 一律拒绝。这把"现在查无"升级为"以后也不会执行"——没有这个保证，死亡判决不成立。
  4. MM 自身的 UNKNOWN 义务（契约新增）MM 对币安提交结果不确定（MM→币安超时）时，不得回报 FILLED / REJECTED，必须保留在途态直到确定——同一问题下推一层，不允许 MM 用猜测关闭自己的窗口。
  5. CANCEL_REJECTED(FILLED) 不能直接忽略本地可能尚未收到全部成交回报（WS 间隙）：先 GET 补齐 fills 序列、逐笔结算后，订单才允许进入终态。
  6. WS 断线 → 重连后全量仲裁重连第一步：对所有在途与 UNKNOWN 状态的 client_order_id 逐个 GET，对齐状态与 fills 序列；fill_id 去重保证不重结算。
  7. 结算幂等双保险connector 合成事件的 IdempotencyKey = client_order_id:fill_id；PM Perp 现有 idempotency cache 天然防重（Settlement.HandleTrade 的 Set/Delete 逻辑复用）。

3.6 我方内部字段的翻译边界

接口保持最小——只传执行必需的字段。以下概念是我方记账内部属性，不出门，由 connector 在合成事件时回填：

我方字段翻译规则
direction (HEDGE long/short)开多→buy；平多(reduce_only)→sell；开空→sell；平空→buy。MM 只见 buy/sell
margin_mode / leverage保证金与杠杆是我方对用户的授信概念；MM 币安侧对冲结构由 MM 自理
position_mode (ONE_WAY/HEDGE)同上，纯内部
reduce_only翻译进 side（见 direction 行）；liquidation 指令带 source 标记优先级
post_only映射 type=POST_ONLY；MM 在币安用 GTX 语义（只挂不吃，否则拒）

INVALID_FILTER数量/价格/名义违反币安过滤器（附 filter 名）判 REJECTED + 解锁；我方 edge 应已前置拦截（第 6 页 exchangeInfo 同步）
MARKET_NOT_SUPPORTEDMM 不支持该市场熔断该市场 + 告警
INSUFFICIENT_LIQUIDITYFOK 无法整单成交判 REJECTED + 解锁（语义正确）
RATE_LIMITED触发限速退避重试
UNKNOWN_ORDER撤单/查询不存在的单走仲裁确认终态
SYSTEM_BUSYMM 内部过载退避；连续出现 → 熔断

过会时需要 MM 逐条确认的点

① GTX（post_only）拒绝时回报里能否区分"会吃单"与其他拒绝原因；② IOC 部分成交的余量是否会推 ORDER_UPDATE(FILLED) + 明确的终态语义（我方余量记 StateExpired，与现网一致）；③ GET /orders 的 fills 列表是否含 role 字段（仲裁补账需要）；④ cancel-all 的生效时延保证；⑤ 币安维护窗口的预告机制；⑥ tombstone 持久化——首次 GET 应答"无记录"后，迟到的同 ID POST 是否保证拒绝（3.5 第 3 条，判死前提）；⑦ MM 侧 UNKNOWN 语义——对币安提交结果不确定时是否承诺不报终态（3.5 第 4 条）。

5 · 结算与账务

MM house 账户：复式记账的最后一块拼图

Principal 模式下，MM 的对冲盈亏发生在币安（他的钱），但我们的账本必须记下对用户的每笔支付义务从哪来。解法：一个新系统账户——MM house 账户——作为每笔成交的对手腿，天然保留 Scheme A 复式记账与审计链。

house 账户定义

沿用现有系统账户机制（raft_recovery/system_accounts.go 的 spec 列表 + EnsureSystemAccounts 幂等对账，UUID 尾号顺延 09）。但 house 位于每一笔成交的热路径上，不能按"新增一个账户"估算——必须按核心结算改造做基准测试与验证（评审意见 2026-09-25）：

// portfolio_manager_perp/perpetuals/domain/models/const.go 新增：
MMHouseAccountAppSessionID = "00000000-0000-0000-0000-000000000009"
MMHouseAccountID          = "00000000-0000-0000-0000-000000000009"
// owner = SystemAccountOwner (0x0)，PrincipalKindService，随 EnsureSystemAccounts 自动建账
  • 语义：余额 = 我们对 MM 的净债务（正 = 我们欠 MM，负 = MM 欠我们）。周期结算时现金清零，余额归入商务结算（条款待决）。
  • 信用敞口 ≠ 余额：熔断线按敞口计 = 已入账余额 + 聚合对冲的未实现 MTM + 未结算 funding 应计。只看余额会在 MM 违约瞬间低估风险——用户的浮盈是我们即将兑付的负债，此刻还没入 house 账。
  • 热点与并发：所有 USDT 计价市场共用一个 house，每笔成交都写它——Raft apply 吞吐与 dbWriter 的 perps_balances 热行 upsert 必须实测。备选：按保险金 Pool 1/2/3 先例做 per-market house 池（与币安 symbol 1:1，对账天然按市场比对，聚合求和即总敞口）。
  • 记账形态：双向 HEDGE 腿：每笔成交原子地同时记用户腿与 house 腿（同一 journal），两侧已实现盈亏严格同步——多用户共用时不会出现时序错位。净仓方案需要改开平判定（IsClosingOrder）语义且破坏该同步性，弃选。house 腿零 allocated margin、零费率。
  • 风控豁免（显式实现，不是默认得到）：允许负余额、无 MMR、不进清算扫描；合成单绕过普通下单校验；以 PrincipalKindService 沿保险金先例排除出用户统计 / 排名 / 奖励 / analytics 聚合。
  • 不重复计账不变量：清算时用户亏损只在成交结算记一次；穿仓差额只由保险金 → house 划转表达，两者不得叠加。配 test/v2 集成场景断言。

经济闭环（一笔用户开多的完整旅程——付款方向已按评审意见修正）

用户开多 10 TAO @199 → 我方锁 IMR → house 对用户记空头腿 → MM 币安买入 10 TAO 对冲。

用户平多 @205 → 合成事件结算：用户 +60（已实现盈亏入账），house −60（按"正 = 我方欠 MM"的约定，负值 = MM 应付我方 60）；MM 币安端对冲盈利 +60。

周期结算：MM 向我方支付 60，我方以此兑现用户盈利。用户亏损时方向相反——house 为正 = 我方欠 MM，从用户收取的亏损金在结算时偿付 MM 的对冲损失。任意时刻 |house 余额| 与 MM 对冲端互为镜像。

两个用户互为对手时（A 买 B 卖）house 两腿轧平，MM 币安端无需下对冲单，点差与费用照收。

funding 透传

  • rate 与周期 — 直接采用币安值：mark oracle 的 funding 字段已有币安源；perps_markets.funding_interval_seconds 已支持可变周期（rollout 已按币安 fundingInfo 种入 4h/8h）。PM Perp 的 funding worker、funding_payments 结算逻辑不变。
  • 账务路径 — 用户付/收资金费计入 house 账户（不再需要向用户对手方收取，因为对手是 house）；MM 币安端对冲的资金费收付与用户侧名义相同时点相同，方向相反自然轧平；残差（用户仓位变动时点差）入 house 余额，随周期结算。
  • cap / 利率 — 透传模式下 cap 恒等于币安实际值，我方不再需要自设 cap（现表值即币安值，无需改动）。

清算与保险金

  1. 扫描器不变 — stage1 cross/isolated executor 的触发判定、MMR 档位、告警带（80/90/95）全部保留。
  2. 平仓出口改变 — 不再发清算 IOC 进 Finex；改为向 connector 提交 source=liquidation 的市价平仓单，MM 币安 unwind 对冲，回报结算（ExecType=liquidation，Scheme A 的 journal_id 归组逻辑复用）。
  3. 穿仓处置 — 用户损失超出其保证金的部分：保险金账户 → house 账户划转（现 CLEARING_MIRROR 的 SettleLiquidatedPosition 路径语义保留，对手从"清算池承接仓位"简化为"差额直付"）。
  4. 退役 — takeover（保险金承接仓位）与 ADL（对手方自动减仓）代码路径下线：A-Book 没有需要保护的内部对手方。保险金唯一职责变为兜穿仓差额。

ledger：外部 K线接入设计（不是"加一个消费者直写"）

评审意见（2026-09-25）：现网 ledger 从 trades 生成连续聚合、高周期再依赖它；外部 1m K线无法仅靠"新增消费者直写"自然接入现有结构——需要新的存储与聚合设计。

  1. 新源表 + UPSERT 语义 — 新增外部 K线源表（symbol, bucket, OHLCV, event_time 水位）：币安 kline 事件携带当分钟累计成交量，未闭合 bar 在当分钟内被逐事件覆盖；重复 / 乱序按事件时间水位幂等 upsert（迟到旧值不回写已更新的 bucket）。
  2. 断线补数 — WS 断线窗口由 REST /fapi/v1/klines 回填，走同一 upsert 路径，天然幂等；补数与实时流竞争时以水位高者胜。
  3. 聚合链重建 — perp 市场的高周期 CAGG 从 trades 源改指向新源表；spot 与过渡期市场保留 trades 链——两条链并存、per-market 路由，不是全局切换。
  4. 历史衔接 — 内部聚合的历史 K线保留，切换日为分界；前端图表跨界拼接（时间轴连续，无重写）。
  5. 用户 trade history — 不受影响：用户自己的成交记录一直由 PM Perp 持有（perps_transactions / position history），与公共 K线互不相干。

admin修改MM 连接状态/对账差异/house 余额监控页；A-book 路由开关操作；对账仲裁工具小
perp_trigger零改动触发→锁仓→命令的既有流程自动流向 connector无
fee_engine / analytics / competitions零改动费用投影与统计照常消费事件（格式未变）；analytics 的 insurance fund equity 视图继续有效无
finex（perp 部分）退役perp shard 下线路由（spot shard 不动）；代码 + 配置保留一个版本周期作回滚开关，之后清理（WAL/快照随实例归档）下线操作

Kafka topic 面变化

不变：commands.{MKT}.OrderCommands（消费者从 finex 换成 connector）、events.{MKT}.EventOrderUpdated / EventTradeExecuted（生产者换成 connector）、orderbook.{MKT}（生产者换成 quote）、perp_trigger.Persistence。新增：events.{MKT}.EventKlineObserved、MM 观测/对账内部 topic。停用：finex perp 的 WAL/快照不再增长。kafka_topic_init 的 -perp-markets 清单不变（topic 均已存在，只是换了生产/消费角色）。

8 · 风险与熔断

单点依赖是最大风险，熔断设计必须先行

A-Book 把"市场风险"换成了"依赖风险"。撮合不再会出错——但 MM 会断连、币安会风控、网线会延迟。这一页的设计目标是：任何单一故障都不造成资金损失，只造成服务降级。

风险清单

风险场景缓解等级
MM 单点MM 断连/系统故障/币安封其账户 → 全站永续无法执行心跳熔断（15s）→ 新单全拒、在途单 cancel-all；SLA 条款；长期解：二级 LP（待决）高
清算遇断连行情暴跌触发连环清算的同一时刻 MM 断连——最危险的组合用户仓位与保证金在我方不受影响（结算暂停而非丢失）；重连后立即补发平仓单；持续恶化由保险金兜底 + 人工升级高
延迟锁仓(Raft ~10ms) + Kafka + connector + MM + 币安 RTT + 回报 → 全链 p99 目标 < 1s；市价单期间价格漂移SLA 分段监控（第 3 页）；市单滑点上限参数（待决）中
滑点吃穿保证金锁仓按下单时校验 IMR，币安成交价劣化 → 成交后 MMR 立即越界 → 秒触发清算锁仓端增加滑点缓冲系数（可配）；越界即走正常清算路径（非资损，是体验问题）；IMR 缓冲值入待决中
UNKNOWN 资金占用仲裁期间保证金保持锁定——网络分区 / MM 不可用时可拖到分钟级对用户呈现"挂单中"；熔断恢复后 UNKNOWN 清算优先于新单；锁仓缓冲含该占用中
对账漂移我方 FSM / MM 报告 / 币安三方状态不一致（网络分区、回报丢失）三级对账 job（第 5 页）+ fill_id 幂等 + GET 仲裁 + admin 冻结工具中
币安平台依赖币安维护窗口 / 风控 / 地域限制直接影响我方全站MM 提供 binance_connected 心跳字段与维护预告；维护期预先熔断（公告停交易）中
MM 违约house 净敞口累积后 MM 拒付/跑路商务保证金条款 + 敞口上限熔断（余额 + 未实现 MTM + funding 应计，见第 5 页；超阈值 → 停止交易并要求补充保证金）（条款待决）商务

熔断矩阵

触发新单在途单清算恢复动作
心跳丢失 15s全拒cancel-all挂起重连 → 全量 GET 仲裁 → 补发清算单 → 解除
连续 429 / SYSTEM_BUSY退避保留重试速率恢复即解除；持续 5 分钟升级为心跳级熔断

人工 kill-switch全拒cancel-all挂起可切回 B-book（一个版本周期内，见第 9 页）

清算挂起的边界说明

挂起期间用户保证金率继续恶化（mark 不停），恢复后按更差价格平仓——保险金吸收的部分会变大，但不会出现无主仓位（我方账本始终自洽）。

这是"服务降级不资损"原则的代价，需纳入保险金容量测算（待决事项）。

9 · 切换计划

六阶段：从清仓到开放

阶段 0–1 是业务与契约（不含代码），阶段 2–3 是工程与联调，阶段 4–5 是生产切换。顺序不可乱，每阶段有明确出口条件。

阶段总览

  1. 阶段 0 · 存量清仓（进行中）内部账户清仓：attacker 已执行（09-22），MM 账户 0x535c / 0x7152 runbook 就绪待执行；普通用户无存量持仓需处置（停服状态视为全新开始，2026-09-24 确认）。出口：全平台 perps 持仓 = 0、订单簿干净。
  2. 阶段 1 · 契约过会（本文档第 3 页）与 MM 逐条过 SLA / 错误码 / 悬挂仲裁语义 / cancel-all 时延 / GTX 拒绝可区分性（3.7 过会清单）；MM 确认实现排期与沙箱环境。出口：双方签字版契约 v1 + MM 沙箱可用。
  3. 阶段 2 · 开发里程碑：① mm-connector MVP（提交/回报/合成事件/幂等）+ mock-MM 模拟器（联调基座，见阶段 3）→ ② PM Perp house 账户 + 清算出口切换 → ③ quote 五路订阅 + ledger K线路径 → ④ 熔断/对账/admin 工具 → ⑤ 端到端用例打通。每里程碑配集成测试进 test/v2 场景。
  4. 阶段 3 · staging 联调（三层测试环境，方案已定）① mock-MM（主力，我方自建）：tools/mockmm 实现契约 v1 的 REST+WS 模拟器，场景注入（多笔成交 / 拒绝 / ack 超时 / 断线重连 / 乱序 / 重复回报 / 429）——CI 可重复，不依赖任何外部环境。② MM 沙箱：MM 按同一契约提供 sandbox；他若接币安 futures testnet（testnet.binancefuture.com，免费 API key）可用 BTCUSDT / ETHUSDT 等主要符号验证真实执行链路——注意 testnet 无 TradFi 合约、深度薄、约月度重置，只验链路不验覆盖。③ 生产小额冒烟：cutover 验证清单内置（受控账户、最小名义）。用例：下单 / 部分成交 / 撤单 / 超时仲裁 / 断线重连 / 清算演练 / 对账差异注入 / 限速退避。出口：全绿 + 双方联调报告。
  5. 阶段 4 · 生产 cutover（顺序铁律）① 公告停新单（trading-api 禁交易开关）→ ② 等在途单终结 / cancel-all → ③ 启用 mm-connector 路由（消费 OrderCommands）→ ④ quote 行情切换（depth/kline/ticker 上线）→ ⑤ finex-perp shard 停止 → ⑥ 验证清单（见下）→ ⑦ 公告开放交易。finex-perp 停在 connector 验证通过之后，顺序反了会出现双消费者。
  6. 阶段 5 · 开放与观察期开放后 72 小时盯盘：延迟分位、对账差异率、费率正确性抽查、清算演练一次（受控账户）。观察期结束 → 移除 B-book 回滚开关的决策评审。

cutover 验证清单

  • 订单簿镜像 — 前端 depth 与币安同 symbol 一致；增量/快照混合流无跳变；延迟 < 300ms。
  • 下单全链路 — 限价挂单/成交、市价多笔成交、post_only 拒绝、FOK 整单拒、IOC 余量过期，五类各至少一笔。
  • 撤单与仲裁 — 正常撤单、撤单竞态（已成交）、人为制造 POST 超时走 GET 仲裁路径。
  • 结算正确性 — 抽查成交的仓位/盈亏/费用（maker/taker 费率按 role）；house 账户余额与手工推演一致。
  • K线连续性 — 切换日前后 1m K线拼接无缺口；高周期聚合正常出值。
  • 清算演练 — 受控账户打到 MMR 触发：平仓单经 MM 执行、ExecType=liquidation、穿仓差额进 house、Scheme A journal 完整。
  • 熔断演练 — 断开 MM 沙箱：15s 熔断生效、新单全拒、cancel-all、重连仲裁恢复。
  • 对账零差异 — 持仓/成交两个 job 首轮全绿。
  • spot 回归（专项） — spot K线连续性抽查；spot 订单簿与公共成交流 cutover 前后基线对照（共享管线的市场类型门控验证）。

回滚（一个版本周期内有效）

# 触发条件：A-Book 出现无法快速修复的系统性问题（对账持续漂移 / MM 长期不可用）
① trading-api 停新单 + cancel-all
② 等在途单终结（若存在持仓：记录并人工对冲决策——回滚要求持仓尽量为零）
③ 路由 flag 切回 finex-perp：connector 停止消费 OrderCommands，finex-perp shard 重启加载市场
④ quote 行情切回（orderbook 生产者换回 finex；K线恢复内部聚合——期间币安 K线已写入的历史保留）
⑤ 验证 → 开放

# 回滚后 A-Book 已发生的历史数据不动（trade history / house 账户余额 / 审计）

回滚的硬约束

回滚时若存在 A-Book 期间开立的持仓，切回 B-book 后 Finex 内部撮合将没有对手流动性——回滚窗口内应把持仓视为需要人工处置的例外。这就是"保留期一个版本周期"的原因：时间越长，回滚的现实性越低，靠观察期把问题暴露在早期。
