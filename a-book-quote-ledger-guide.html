任务的本质

A-Book 市场的成交发生在币安，内部 trades 会变得稀疏（只剩用户自己的成交）——用它们聚合 K 线就是假 K 线；同时内部订单簿不再存在。所以：quote 直接搬币安全量行情（深度 / K 线 / ticker / 成交带 / 过滤器），ledger 直接吃币安的 K 线。

下游（trading-api / PM Perp）零改动——因为事件格式和 topic 完全不变。这是整个任务的验收标准。

quote 服务：三层结构

quote 不碰用户数据、不写数据库，是纯流处理器。代码在 quote/，配置在 nacos configs/nacos/quote.yaml。

引擎层（quote/engine/）

engine.go 的 Engine 管理一组行情源并搭起计算流水线。所有行情源实现同一个 20 行的接口 provider.Source（quote/engine/provider/interface.go）：Subscribe(market) / Subscriptions() / Done()。加新数据源 = 实现这个接口。

Provider数据现状
binance_spot币安现货成交流现货价候选源
coinapi多所现货成交聚合现货价主源（付费）
binance_perp币安合约现在只订 markPrice 流，nacos 里只配了 btc/usdt、eth/usdt——这是你要扩展的
bitfaker合成数据测试用

两条处理路径（engine.go:201 的 switch，:309 分叉）

路径流向
trades 路径（现货）trades → router.go 按市场分 channel → 聚合器（100ms 窗口，按价格+方向合并）→ 指标（VWMA / momentum / moving_std，indicator/ 目录）→ outbox
mark price 路径（合约）binance_perp 的 EventMarkPrice 不走指标，直接 SinkMarkPrice 进 outbox

引擎配置全部来自 quote.yaml 的 engine: 段：providers 列表、markets、symbol_aliases_perp（BTCUSDT → BTCUSDT-PERP 的映射就在这里）、每个 provider 自己的 markets 覆盖。

发布层（quote/quotes_publisher.go）

QuotesService.Run 消费引擎 outbox，发 Kafka：trades 发现货价；mark price 发同一个 topic 但带 mark / index / funding 三个字段，市场名经 resolveSymbolPerp（:113）映射成 BTCUSDT-PERP（:254-262）。

mark 价体系（quote 里最复杂的部分，但有现成钩子）

mark 价有两代系统并存：

代际位置机制
老quote/markoracle/Coordinator + binance / okx / bybit 三个 collector，采样发 events.MarkPriceSample

internal_perp_trade 这个源

markoracle/internal_perp_trade_collector.go 把「内部成交」当价格源。A-Book 市场成交搬去币安后它就没有信息量了——任务之一是按市场停用它。

ledger 服务：纯消费者 + 读服务

ledger 只做两件事：把内部成交变成 K 线，把 K 线和 ticker 提供出去。代码在 ledger/，存储用 TimescaleDB（Postgres + 时序扩展）。

为什么这个任务不是「加个消费者直写」

K 线 100% 由内部 trades 聚合，高周期全部构建在 ohlc_1m 之上。A-Book 市场的成交在币安，内部 trades 稀疏，聚合出的 K 线没有代表性。但 spot 和 B-Book perp 市场仍然要走 trades 链。

所以是两条聚合链并存、按市场路由：perp A-Book 市场的聚合源改指向币安 K 线源表，spot / B-Book 市场的 trades 链原封不动。这是存储与聚合的重设计，不是加一个消费者。

动手顺序与铁律

先花一天建立「一条事件的完整旅程」的认知，再按 mirror → kline → 收尾的顺序推进。每个阶段都有可验证的产出。

四周计划

  1. 第 0 天 · 建立认知（不改代码）对着 nacos quote.yaml 的 engine: 段读三条路径：① binance_perp/binance.go → client.go → websocket.go（一条 markPrice 从币安 WS 到 Kafka 的完整路径）；② quotes_publisher.go（EventQuoteObserved 怎么发）；③ ledger/event/consumer.go → consumer/trade.go（一条成交怎么落 trades 表）。
  2. 第一周 · 镜像先行book 开关进市场元数据（对齐任务 1）+ depth20 镜像 + orderbook 复刻（Q1 / Q2 / Q4）——前端最直观、联调最早要用。产出：staging 里能看到币安深度的镜像簿。
  3. 第二周 · K 线链路EventKlineObserved 协议（对齐任务 5）+ ledger 源表 migration + UPSERT / 水位 + REST 补数（Q3 + L1 / L2 / L3）。产出：币安 K 线进 Timescale。
  4. 第三周 · 收尾双链路由 + 24h ticker 换源 + mark 按市场切换 + collector 停用（L4 / L5 / L6 + Q5 / Q6）。产出：集成测试（testcontainers）+ B-Book / spot 回归报告。

三条铁律

① 格式不变

发出去的 topic 和事件格式必须和现在一模一样：orderbook 增量与 Finex 现有格式逐字段一致，EventQuoteObserved / EventTickerUpdated 不改结构。下游（trading-api / PM Perp / ledger 消费端）零改动是验收标准。

② 按市场门控，绝不全局切换

spot 和 B-Book perp 的路径语义一个字节都不能变。所有新逻辑挂在「A-Book 市场」的开关后面；设计文档第 6 页的 spot 边界矩阵是验收清单。

③ displayed = enforced

你发布的 mark 就是 PM Perp 强平用的 mark。A-Book 市场必须严格等于币安 mark——权重 100%，不许混合。否则会出现「用户看到价格没到强平价，却被强平了」。
