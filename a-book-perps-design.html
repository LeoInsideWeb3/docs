1 · 总览与决策

永续全面转向 A-Book

平台退出永续对手方角色：订单簿、K线、24h 统计直接采用币安数据；用户订单全部经我方自有做市商（MM）在平台自己的币安主账户上真实执行；平台保留账户、保证金、强平价计算与手续费体系，赚取显式手续费，不再承担内部撮合与对手方市场风险。v1.4 起 A-Book 仓位一律逐仓 + 单向持仓：每个仓位的强平价由我方计算，MM 在币安挂一张对应的止损单，止损单的真实成交就是用户的强平。

决策点结论含义
币安账户我方自有主账户所有用户订单落在同一个平台自有币安账户；币安只看得到这个账户的净头寸和余额，看不到单个用户（2026-09-28 决定）
MM 角色自有执行代理我方自己的 MM 系统操作主账户：转发用户订单、持有强平止损单。它不是对手方——没有商务结算，也没有 MM 信用敞口
保证金与持仓模式强制逐仓 + 单向A-Book 市场关闭全仓与双向持仓；一个用户 × 一个币对最多一个仓位 = 一个强平价（2026-09-28 决定）
强平执行本地算价 → 币安止损单PM Perp 计算每个仓位的逐仓强平价并发布；MM 在币安挂单并维护；止损单的实际成交价就是用户的强平价
成交价格币安真实成交价 + 显式手续费费率走 fee_engine 现有体系；点差不进价格
切换范围全量切换所有永续市场一次切 A-Book；无存量持仓（从新开始）
行情与映射以币安为准执行 / 行情 / K线 / mark 价全以币安为准；仅维护我方 ↔ 币安 symbol 映射
接口现状NeoDAX ↔ MM 未建MM 已对接币安；我方与 MM 之间的契约（订单 + 强平保护）= 本文档第 3 页（过会材料）

三个必须先说清楚的前提

前提一：切换时点全平台持仓必须为零（已确认从新开始）

切换瞬间全平台无未平仓位——历史持仓没有币安对冲，账实分离。

内部账户清仓进行中：attacker 已执行（09-22），0x535c / 0x7152 runbook 就绪。普通用户无存量持仓需处置（停服状态视为全新开始，2026-09-24 确认）。

前提二：用户条件单留在本地；强平改为币安上的止损单

用户止盈止损的触发判定、WAL、LockPerpAsset 仍在本地（perp_trigger 的 Trigger→Lock→CommandOrderExecute 流程不变）。

强平形态改变（v1.4）：PM Perp 继续计算每个仓位的逐仓强平价（MMR 档位），但不再自己发平仓单——它把强平价作为保护目标发布，由 MM 在币安的止损单完成平仓。扫描器保留为影子监控（只报警），同一个仓位不会被平两次。

前提四：逐仓 + 单向是强制的，不是默认值

A-Book 市场在服务端拒绝全仓和双向持仓设置（PM Perp + trading-api 校验），前端隐藏 Cross/Hedge 切换。一个用户 × 一个币对最多一个仓位，对应恰好一个强平价、一张止损单。

前提三：保留一个版本周期的 B-book 回滚开关

finex-perp 引擎下线路由但不删代码。

cutover 后保留一个版本周期的"路由 flag 热切回 Finex"能力（第 9 页），观察期结束、A-Book 稳定后再清理。

↓ Kafka commands.{MKT}.OrderCommands（同一 topic，消费者换人）

↓ REST / WS（第 3 页契约） · MM → 币安执行

仍消费 EventTradeExecuted 做双参与者结算——只是对手腿从"另一个用户/系统账户"固定为 house 系统账户（UUID 尾号 09，owner=0x0），它镜像我方币安主账户。每次仓位变化后重算逐仓强平价，向 connector 发出保护目标；强平成交以 ExecType=liquidation 回来。takeover/ADL 退役，保险金只兜穿仓差额。

↓ 币安公共流（quote 镜像，第 6 页）
quote + ledger数据面切换

quote 订阅币安 depth/kline/ticker/aggTrade，以现有格式发布；ledger 的 perp 市场 K线数据源从"内部成交聚合"切到"币安 K线直写"（per-market 开关）；InternalPerpTradeCollector 对 A-book 市场停用。

为什么否决 Kafka-native 方案

另一条路是让 MM 直接消费/生产我们的 Kafka topic（省掉 connector）。否决理由：

  1. 安全边界 — 需要把 Kafka 集群网络与凭证暴露给 MM 的服务（虽是自有，但是独立运维的系统），consumer group、rebalance、lag 管理责任全部外移，事故面不可控。
  2. 耦合演进 — 内部事件 schema（如 EventTradeExecuted 加字段）会直接破坏外部消费者；REST/WS 契约让我们可以独立演进内部格式。
  3. MM 实现成本 — MM 团队熟悉的是币安式 REST/WS。接口语义镜像币安（下单/撤单/执行流），他们的实现几乎是零学习成本。
  4. 治理 — connector 是我们的一等公民服务：限速、熔断、对账、审计日志都在我们侧，可观测可运维。

3.0 数据所有权：谁存什么，谁说了算

先回答一个架构级问题：用户的一切状态都存在我方，MM 只是执行反馈的来源。用户侧任何读写都不透传到 MM——这是本契约刻意保持最小（提交 + 回报 + 对账）的原因。

数据权威归属说明
用户订单 / 仓位 / 余额 / 成交历史我方 PM Perpperps_orders / perps_positions / perps_balances / perps_transactions + Raft FSM——现网结构不变
用户读接口（REST / WS 私有流）我方本地trading-api → PM Perp gRPC，与现网一致；永不查 MM——MM 挂了只影响下单，不影响查询
MM 侧订单 / 仓位状态MM（执行反馈）只是我方状态机的输入，不是账本；GET 仅用于仲裁与对账（见下）
每个仓位的强平价我方 PM Perp本地计算（逐仓公式 + MMR 档位）；展示给用户的和发给 MM 的是同一个值
币安止损单（强平保护）MM（挂单与维护）止损单在币安上怎么挂由 MM 负责（Algo 接口、替换顺序、限频）；我方负责目标值，并通过对账核验（3.8）

3.4 WebSocket 执行流（WS /api/v1/stream）

connector 全程保持一条 WS（断线重连后先对在途与 UNKNOWN 单跑一轮 GET 仲裁再恢复）。消息信封：{type, client_order_id, mm_order_id, transact_time, ...}。

type触发专有字段

ORDER_REJECT异步拒绝error_code, message

CANCEL_REJECTED撤单失败reason(FILLED|UNKNOWN_ORDER|...)

{

  "client_order_id": "3f9c2a48-...",
  "fill_id":         "MM-F-001283",   // MM 侧唯一，幂等去重用
  "qty":             "5.00",
  "price":           "199.40",         // 币安成交价（可能多笔不同价）
  "role":            "taker",          // maker|taker → 决定我方收哪种费率
  "transact_time":   "2026-10-01T08:00:00.871Z"
}

为什么 role 重要

我方锁仓时按订单类型预收费率（post_only 按 maker 锁），结算时按 MM 回报的币安成交角色计费：限价单挂上后被动成交 → role=maker → 收 maker 费率；吃单 → taker 费率。与现网 Finex 的 maker/taker 语义完全对齐，fee_engine 无需改动。

3.5 幂等 · 悬挂 · 仲裁

必须关闭的竞态窗口（评审意见 2026-09-25）

500ms 时 GET 查无记录 ≠ 该单不会执行：POST 可能仍在网络或 MM 队列里，800ms 才到达且未过期（默认有效期 3s）——若此时解锁保证金、用户转走资金，随后到达的成交将没有保证金背书。expires_at 只约束"MM 收到时"，不约束"我方何时可判死"。

  1. 提交即带 expires_at（我方时钟 + 2 × RTT + 处理余量，默认 3s）MM 收到时已过期的请求必须返回 EXPIRED 拒单且不得执行——有效期是死亡判决的时间前提，不是充分条件（见第 2 条）。
  2. ack 超时（500ms）→ 订单进入 UNKNOWN，保证金保持锁定超时只说明"没等到 ack"，不说明"MM 没收到"。判死必须同时满足三个条件：① 已过 expires_at + 时钟偏移余量（默认 +1s）；② 此时 GET 仍无记录；③ MM 对该 client_order_id 提供不可再执行的终态保证（tombstone，第 3 条）。未到期前的"查无"一律视为 UNKNOWN 持锁，对用户呈现为 pending。
  3. MM 侧 tombstone 保证（契约新增）MM 首次对某 client_order_id 应答 GET "无记录"时必须持久化该应答；此后迟到的同 ID POST 一律拒绝。这把"现在查无"升级为"以后也不会执行"——没有这个保证，死亡判决不成立。
  4. MM 自身的 UNKNOWN 义务（契约新增）MM 对币安提交结果不确定（MM→币安超时）时，不得回报 FILLED / REJECTED，必须保留在途态直到确定——同一问题下推一层，不允许 MM 用猜测关闭自己的窗口。
  5. CANCEL_REJECTED(FILLED) 不能直接忽略本地可能尚未收到全部成交回报（WS 间隙）：先 GET 补齐 fills 序列、逐笔结算后，订单才允许进入终态。
  6. WS 断线 → 重连后全量仲裁重连第一步：对所有在途与 UNKNOWN 状态的 client_order_id 逐个 GET，对齐状态与 fills 序列；fill_id 去重保证不重结算。
  7. 结算幂等双保险connector 合成事件的 IdempotencyKey = client_order_id:fill_id；PM Perp 现有 idempotency cache 天然防重（Settlement.HandleTrade 的 Set/Delete 逻辑复用）。

3.8 强平保护契约（v1.4）

2026-09-28 确定的分工：我方计算强平价，MM 在币安按这个价格维持一张止损单。我方按仓位发布期望状态，MM 把币安收敛到这个状态。我方自己从不在币安挂、改、撤止损单。

// PUT /api/v1/protections/{position_key} —— position_key = {app_session_id}:{market}
{
  "position_key":  "8c1e…:TAOUSDT-PERP",
  "version":       1042,                      // 每个仓位单调递增；旧版本必须丢弃
  "binance_symbol": "TAOUSDT",
  "side":          "sell",                    // 平仓方向：多仓 → sell，空仓 → buy
  "qty":           "19.75",                   // 仓位全量；"0" = 撤销保护
  "trigger_price": "181.35",                  // 我方计算的逐仓强平价
  "working_type":  "MARK_PRICE",              // 与展示给用户的 mark 同一参照
  "reason":        "fill"                     // fill|margin_change|leverage|funding|resync
}

// 3.4 执行流新增的 WS 回报
PROTECTION_APPLIED   {position_key, version, binance_stop_id, trigger_price, qty}
PROTECTION_TRIGGERED {position_key, version, binance_stop_id, transact_time}   // 先于成交回报发出
TRADE_FILL           {…, source:"liquidation", position_key, version}          // 平仓成交，3.4 格式
PROTECTION_REJECTED  {position_key, version, error_code}                       // 如达到上限 —— 告警

我方义务

  • 每次变化都发布 — 每笔成交（含部分成交）、追加/减少保证金、改杠杆、资金费结算、会影响强平价的扣费之后。仓位归零 → 发布 qty=0。
  • 我方也做合并 — 每个仓位同时最多一个未完成的版本；新目标在发出前覆盖旧目标。MM 仍然只执行它见过的最高版本。
  • 定期全量重发 — 每 N 分钟以及每次 WS 重连后，把所有持仓的最新版本重发一遍（MM 侧幂等）。
  • 触发即冻结 — 收到 PROTECTION_TRIGGERED 后，仓位进入强平中状态（沿用现有逐仓强平锁）：在强平结算完成前，拒绝该用户在这个币对上的新订单。

MM 义务（过会逐条确认）

  • 每个仓位恰好一张生效止损单 — 替换顺序是先撤后挂，绝不先挂后撤：同时存在两张止损单时可能都触发，等于把仓位平两次。先撤后挂的短暂无保护空窗可以接受。
  • 撤单返回"未知订单" = 可能已触发 — 旧单的结果确定之前不挂新单（如果已触发，改为回报强平）。
  • 价格已经穿过 — 如果币安因为触发价会立即触发而拒绝止损单，立刻按市价平仓，并作为强平回报。
  • 补足全部数量 — 止损单触发后只部分成交时，继续按市价平掉剩余数量，直到被保护的数量全部平完；最后一笔成交标记为 final。
  • 净额账户规则 — 主账户是所有用户的净额：不得使用 closePosition 和按 symbol 全撤，也不要依赖 reduceOnly（三者作用的都是账户净头寸，也就是会波及其他用户）。
  • 币安限制由 MM 解决，但要对我方可见 — 条件单现在走 Algo Service（/fapi/v1/algoOrder，clientAlgoId），且币安限制每个账户每个 symbol 的条件单数量（撰写时为 10 张），远少于"每个用户一张"。MM 怎么覆盖所有仓位（子账户、本地触发……）是它的设计选择，但保护不了的仓位必须通过 PROTECTION_REJECTED 报出来，绝不能静默丢弃。
  • 归属 — 每张止损单和每笔强平成交都带 position_key + version，成交能直接结算到正确的用户，不需要解析币安 id。

强平价定义（逐仓、单向）

复用 PM Perp 现有的逐仓强平价计算（就是现在展示给用户的那个值），MMR 取市场的风险档位。参考公式：多仓 ≈ (开仓价 × 数量 − 逐仓保证金) / (数量 × (1 − MMR))；空仓 ≈ (开仓价 × 数量 + 逐仓保证金) / (数量 × (1 + MMR))。其中逐仓保证金已计入追加或减少的保证金、收付的资金费和扣除的手续费。触发点设在维持保证金水平而不是破产价，为触发到成交之间的滑点留出缓冲。

5 · 结算与账务

house 账户：复式记账的最后一块拼图

每笔用户成交都是我方自有币安主账户上的真实交易，但我们的账本必须记下对用户的每笔支付义务从哪来。解法：一个新系统账户——house 账户——作为每笔成交的对手腿。它是主账户在账本里的镜像，天然保留 Scheme A 复式记账与审计链。

house 账户定义

沿用现有系统账户机制（raft_recovery/system_accounts.go 的 spec 列表 + EnsureSystemAccounts 幂等对账，UUID 尾号顺延 09）。但 house 位于每一笔成交的热路径上，不能按"新增一个账户"估算——必须按核心结算改造做基准测试与验证（评审意见 2026-09-25）：

// portfolio_manager_perp/perpetuals/domain/models/const.go 新增：
MMHouseAccountAppSessionID = "00000000-0000-0000-0000-000000000009"
MMHouseAccountID          = "00000000-0000-0000-0000-000000000009"
// owner = SystemAccountOwner (0x0)，PrincipalKindService，随 EnsureSystemAccounts 自动建账
  • 语义：house = 我方币安主账户在账本里的镜像。它的已实现盈亏等于主账户在用户流量上的交易盈亏；它在每个市场的持仓等于用户总持仓的相反数。没有第三方需要结算：house 余额与主账户钱包对账，不对外支付。
  • 主账户保证金是平台级风险：逐仓只存在于我方账本。在币安上所有净头寸共用一个账户的保证金，主账户本身可能被强平。需要监控主账户保证金率并设熔断（第 8 页）；主账户在币安上的杠杆与保证金设置是运营决策，不从用户推导。
  • 热点与并发：所有 USDT 计价市场共用一个 house，每笔成交都写它——Raft apply 吞吐与 dbWriter 的 perps_balances 热行 upsert 必须实测。备选：按保险金 Pool 1/2/3 先例做 per-market house 池（与币安 symbol 1:1，对账天然按市场比对，聚合求和即总敞口）。
  • 记账形态：双向 HEDGE 腿：每笔成交原子地同时记用户腿与 house 腿（同一 journal），两侧已实现盈亏严格同步——多用户共用时不会出现时序错位。净仓方案需要改开平判定（IsClosingOrder）语义且破坏该同步性，弃选。house 腿零 allocated margin、零费率。
  • 风控豁免（显式实现，不是默认得到）：允许负余额、无 MMR、不进清算扫描；合成单绕过普通下单校验；以 PrincipalKindService 沿保险金先例排除出用户统计 / 排名 / 奖励 / analytics 聚合。
  • 不重复计账不变量：清算时用户亏损只在成交结算记一次；穿仓差额只由保险金 → house 划转表达，两者不得叠加。配 test/v2 集成场景断言。

funding 透传

  • rate 与周期 — 直接采用币安值：mark oracle 的 funding 字段已有币安源；perps_markets.funding_interval_seconds 已支持可变周期（rollout 已按币安 fundingInfo 种入 4h/8h）。PM Perp 的 funding worker、funding_payments 结算逻辑不变。
  • 账务路径 — 用户付/收资金费计入 house 账户。币安按主账户的净头寸收付，我方按每个用户各自的仓位收付；用户多空都有时两者不同（多空在币安上相互抵消，在我方各自收付）。差额是 house 盈亏，每次资金费结算显式入账，并与主账户在币安的资金费记录对账。
  • 强平价随资金费变化 — 每次资金费结算都会改变逐仓保证金，所有持仓重算一遍并批量发布新的保护版本。只有强平价变动超过阈值（N 个 tick）的仓位才重发，并且分批限速，避免在资金费时点撞上币安限频。
  • cap / 利率 — 透传模式下 cap 恒等于币安实际值，我方不再需要自设 cap（现表值即币安值，无需改动）。

清算与保险金

  1. 强平价是输出 — MMR 档位与逐仓公式保留；扫描器不再决定何时平仓，而是计算并发布强平价（3.8），同时做影子监控（第 4 页）。
  2. 在币安执行 — MM 的止损单按币安真实成交价平仓；回报的成交按 ExecType=liquidation 结算（Scheme A 的 journal_id 归组逻辑复用）。这个成交价就是用户在历史记录里看到的强平价。
  3. 结算顺序 — 已实现盈亏 → 强平手续费 → 剩余逐仓保证金退回用户可用余额 → 撤掉该用户在这个币对上的其他订单（第 4 页）。
  4. 穿仓处置 — 用户损失超出其逐仓保证金的部分：保险金账户 → house 账户划转（现 CLEARING_MIRROR 的 SettleLiquidatedPosition 路径语义保留，对手从"清算池承接仓位"简化为"差额直付"）。逐仓把用户的损失限制在这一个仓位的保证金内。
  5. 退役 — takeover（保险金承接仓位）与 ADL（对手方自动减仓）代码路径下线：A-Book 没有需要保护的内部对手方。保险金唯一职责变为兜穿仓差额。

8 · 风险与熔断

单点依赖是最大风险，熔断设计必须先行

链路中断的边界说明

保护挂在币安上，所以 NeoDAX ↔ MM 中断不再让清算挂起：已生效的止损单照常触发，回报恢复后再结算。真正的敞口在 MM ↔ 币安一侧——最新目标从未生效的仓位，或币安不接受的止损单。

影子扫描器、保护对账和紧急平仓工具就是为这些空窗准备的；剩余成本需纳入保险金容量测算（待决事项）。

cutover 验证清单

  • 订单簿镜像 — 前端 depth 与币安同 symbol 一致；增量/快照混合流无跳变；延迟 < 300ms。
  • 下单全链路 — 限价挂单/成交、市价多笔成交、post_only 拒绝、FOK 整单拒、IOC 余量过期，五类各至少一笔。
  • 撤单与仲裁 — 正常撤单、撤单竞态（已成交）、人为制造 POST 超时走 GET 仲裁路径。
  • 结算正确性 — 抽查成交的仓位/盈亏/费用（maker/taker 费率按 role）；house 账户余额与手工推演一致。
  • K线连续性 — 切换日前后 1m K线拼接无缺口；高周期聚合正常出值。
  • 逐仓 / 单向强制 — 每个 A-Book 市场都拒绝全仓和双向持仓请求；界面隐藏切换开关。
  • 保护生命周期 — 开仓 → 止损单按发布价生效；多次部分成交合并成一次替换；追加保证金 / 改杠杆会移动止损单；平到零会撤掉它；保护对账全绿。
  • 清算演练 — 受控账户的仓位打到强平价：币安止损单触发，成交以 ExecType=liquidation 按真实成交价回来，剩余保证金退回，这个币对上的其他订单被撤掉，穿仓差额（如有）进 house，Scheme A journal 完整。
  • 资金费重算 — 资金费结算后，受影响仓位在限速批次内拿到新的保护版本；没有限频错误。
  • 熔断演练 — 断开 MM 沙箱：15s 熔断生效、新单全拒、cancel-all、重连仲裁恢复。
  • 对账零差异 — 所有 job（净头寸 / 保护 / 成交 / 钱包）首轮全绿；主账户保证金率在区间内。
  • spot 回归（专项） — spot K线连续性抽查；spot 订单簿与公共成交流 cutover 前后基线对照（共享管线的市场类型门控验证）。

回滚（一个版本周期内有效）

# 触发条件：A-Book 出现无法快速修复的系统性问题（对账持续漂移 / MM 长期不可用）
① trading-api 停新单 + cancel-all
② 等在途单终结（若存在持仓：记录并人工对冲决策——回滚要求持仓尽量为零）
③ 路由 flag 切回 finex-perp：connector 停止消费 OrderCommands，finex-perp shard 重启加载市场
④ quote 行情切回（orderbook 生产者换回 finex；K线恢复内部聚合——期间币安 K线已写入的历史保留）
⑤ 验证 → 开放

# 回滚后 A-Book 已发生的历史数据不动（trade history / house 账户余额 / 审计）

回滚的硬约束

回滚时若存在 A-Book 期间开立的持仓，切回 B-book 后 Finex 内部撮合将没有对手流动性——回滚窗口内应把持仓视为需要人工处置的例外。这就是"保留期一个版本周期"的原因：时间越长，回滚的现实性越低，靠观察期把问题暴露在早期。
