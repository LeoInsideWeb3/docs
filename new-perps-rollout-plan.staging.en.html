Rollout Runbook for 5 Perpetual Markets (Staging)

This is the staging rehearsal before the production rollout and covers 5 markets (production: 14). None of these markets has been launched to users yet. They are initialized in PM Perp directly as A_BOOK, executed by MM Connector, with Quote mirroring Binance market data. There is no existing B-book routing, so do not run marketctl book-switch and do not add them to any Finex shard.

Safety boundary

The database row may be status=active so services can discover the market, but the first write must be operational_state=FROZEN. Only after market data, connector, Kafka, risk and account checks pass, switch each market to OPEN through the Admin A-book state API, one at a time.

Four principles

Execution ownershipexecution_book=A_BOOK and desired_execution_book=A_BOOK. Finex must ignore these markets when it receives MarketSync.
Price ownershipMark, order book, trade tape, kline and ticker all come from the matching Binance USD-M symbol. The Binance weight of the A-book mark is 1.0.
Margin modeA-book allows isolated only. Cross-margin orders must be rejected, and the default market setting must resolve to isolated.
One market at a timeValidate while FROZEN, then OPEN a single market; move to the next only after a full observation window.

Do not

Run book-switch; add these markets to any Finex configured_markets; reuse generic risk tiers from older documents; use an OKX/Bybit blended price for A-book liquidation; or open a market without a Binance leverage bracket snapshot.

Release-day Snapshot and Gates

The static table is for review only. The actual seed must be generated from, or diffed field by field against, the release-day snapshot; external parameters can change at any time.

# Public parameters (keep raw responses, UTC time and SHA-256)
curl -fsS 'https://fapi.binance.com/fapi/v1/exchangeInfo' -o exchangeInfo.json

sha256sum exchangeInfo.json fundingInfo.json premiumIndex.json

# Risk brackets (USER_DATA signed endpoint; read-only key; never post responses to public logs)
GET /fapi/v1/leverageBracket?symbol=<BINANCE_SYMBOL>&timestamp=<ms>&signature=<HMAC>

Gates

  • STOPAny symbol is not TRADING, or its contract type is not as expected.
  • STOPSeed tick / step / min / max / notional / percent-price / funding / interest / liquidation fee differs from the snapshot.
  • STOPAny leverage bracket is missing, tiers are not contiguous, or max_net_notional exceeds the allowed cap.
  • STOPThe Binance execution account lacks trading permission, isolated setting or sufficient margin for the symbol.
  • PASSRaw JSON, extracted table, SHA-256 and reviewer for all 5 symbols are recorded in the release ticket.

Ensure the System House Account Exists

The shared A-book House account must exist in both the PM Perp database and the Raft FSM. Both account_id and app_session_id are fixed to 00000000-0000-0000-0000-000000000009, and owner is the zero address. Do not seed or open any market until this check passes.

4.1 Check the leader startup log

kubectl logs -n <namespace> <leader-pod-name> | grep "\[SYSTEM_ACCOUNTS\]"

Healthy

[SYSTEM_ACCOUNTS] account present in FSM and DB, no action needed
[SYSTEM_ACCOUNTS] all system accounts verified present in FSM

The first line is a Debug log. When Debug is not enabled, seeing only the final all system accounts verified line is also healthy.

Auto-repaired present in DB, missing from FSM

[SYSTEM_ACCOUNTS] account found in DB but missing from FSM, registering into FSM
[SYSTEM_ACCOUNTS] account registered into FSM successfully
[SYSTEM_ACCOUNTS] all system accounts verified present in FSM

Auto-repaired present in FSM, missing from DB

[SYSTEM_ACCOUNTS] account found in FSM but missing from DB, back-filling database record
[SYSTEM_ACCOUNTS] database record back-filled successfully
[SYSTEM_ACCOUNTS] all system accounts verified present in FSM

Failure (startup aborts)

[SYSTEM_ACCOUNTS] CRITICAL: system account missing from FSM after reconciliation

If this line appears, or the final all system accounts verified present in FSM line is missing, stop the release immediately. Do not seed or OPEN.

4.2 Repair system accounts without downtime

Run against the current Raft leader only. It reconciles all required system accounts (including the A-book House) and fills the DB or the FSM in whichever direction is missing. Safe to repeat.

Post-repair gate

Re-run the log check in 4.1 and confirm all system accounts verified present in FSM. If the response is not leader, locate the leader and retry. Any success: false means the repair did not succeed.

Deployment Order

Make every service capable of carrying the markets first, then write the markets; warm up, then validate. Stay FROZEN throughout.

  1. Merge and deploy config, with markets still undiscovered / closedDeploy Kafka provisioning, Quote, Ledger, Trading API and MM Connector first. Do not run the market seed yet.
  2. Create and verify topicsThe topic provisioning Job must succeed; spot-check partition / retention settings for each A-book topic type.
  3. Apply the PM Perp migration and seedThe 5 markets enter A_BOOK + ACTIVE routing + FROZEN. Confirm CommandMarketSync was published and Finex does not hold these markets.
  4. Wait for data warm-upQuote builds the REST depth snapshot + diff stream; Ledger receives external kline / ticker; PM Perp receives fresh Binance mark and funding; Connector starts consuming and keeps heartbeating.
  5. Run the FROZEN acceptanceVerify parameters, route version, account permissions, risk snapshot, market data latency, order book sequence, reconciliation baseline and alerts.

Suggested waves

Open one crypto canary first (suggested: ARB); after it is verified, open UNI, AAVE, XAU and GOOGL one by one. Change one market at a time. Never OPEN all 5 in parallel.

After each OPEN you must see

execution_book=A_BOOK, routing_state=ACTIVE, operational_state=OPEN, connector consuming=true, circuit_state=CLOSED, no route version drift, and Kafka offsets advancing.

←07Deploy order09Acceptance →

Per-market Acceptance Checklist

Check every item after each OPEN. Move to the next market only after all pass and the observation window has elapsed.

  • Tick, step, min qty, min notional, max leverage and all risk tiers shown in exchange info match the Binance snapshot field by field.
  • Mark is sourced from Binance with fresh timestamps; the top 50 order book levels, trade tape, 1m kline and 24h ticker keep updating.
  • Cross-margin orders are rejected; small isolated limit and market orders execute, with quantities on step and prices on tick.
  • The signed sum of NeoDAX user positions and the House position is 0; connector external fills map one-to-one to internal fills, with no reconciliation diff.
  • Cancel, reduce-only, trigger, funding and liquidation flows must all pass on staging (including destructive liquidation tests); the results are the evidence required before the production rollout.
  • Requests with invalid precision, below min notional, above max leverage / tier, or above max net notional all fail closed.
  • No disconnected, stale risk, margin ratio, position invariant or liquidation timeout alerts during the observation window before opening the next market.

Rollback and Incident Handling

On failure, freeze first and preserve evidence, then repair along the A-book path. Rollback never changes execution ownership.

  1. FROZEN immediatelyUse the same A-book state API to set the market to FROZEN. Do not book-switch to B-book.
  2. Preserve evidenceRecord the operation id, route version, connector offsets, orders and fills, external account snapshot, reconciliation diff, market data sequence and alert timeline.
  3. Handle exposureWhile user / House / external positions exist, stay FROZEN and repair through the A-book cancel-all / reconcile / reconcile-order paths. Never delete the market or reset the route version.
  4. Revert config only from zero stateOnly after confirming zero positions, zero orders, zero triggers, zero unsettled funding and no external exposure may the market be disabled and removed from edge / market data subscriptions.
  5. Parameter changesIf Binance changes filters, funding or brackets during the rollout, freeze the affected markets, generate a new snapshot and a new config version, and OPEN again only after the diff is reviewed.

Final rule
